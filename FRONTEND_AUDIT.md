### Architectural Relationship of the Three Surfaces

```
[Repository Root]
├── defense_radar_system/
│   ├── server.js (Express + WS on :8080) <─── AUTHORITATIVE BACKEND & ENGINE
│   ├── public/ <───────────────────────────── AUTHORITATIVE FRONTEND (Surface 1)
│   │   ├── index.html (All 7 Pages / Workspaces)
│   │   ├── js/ (app.js, radar.js, spectrum.js, camera.js, analytics.js)
│   │   └── css/ (styles.css)
│   ├── test/ (run_all_tests.js, test_final_presentation_acceptance.js)
│   └── package.json
│
├── radar-scanner/ (Surface 2)
│   ├── Vite + React 18 + Tailwind (port 5173)
│   └── Connects to http://localhost:8080/api and ws://localhost:8080/ws/c2
│       (Isolated secondary React client demonstrating modular API consumption)
│
├── public/ & api/ & index.js (Surface 3)
│   ├── index.js -> Delegates directly to require('./defense_radar_system/server.js')
│   ├── package.json -> "build": "copyfiles -u 2 defense_radar_system/public/**/* public"
│   └── Vercel / Cloud deployment packaging wrapper
```

1. **Surface 1 (`defense_radar_system/public/`)**: This is the **primary, authoritative monolithic single-page application** containing all 7 tactical workspaces shown in the 7 screenshots. It renders the PPI radar canvas, EW spectrum waterfall, optical horizons, sensor fusion matrix, adaptive MAB scheduler, benchmarks, and simulation suite.
2. **Surface 2 (`radar-scanner/`)**: An independent React 18 + Vite client running on port 5173. It consumes the same backend REST API (`/api/*`) and WebSocket feed (`/ws/c2`) from `defense_radar_system/server.js`. It renders a modern React-based tactical track list, personnel roster, and single-screen radar display.
3. **Surface 3 (Root `public/`, `api/`, `index.js`, `vercel.json`)**: A serverless/monorepo hosting harness. The root `package.json` contains `"build": "copyfiles -u 2 defense_radar_system/public/**/* public"`. Root `index.js` boots `defense_radar_system/server.js`.
4. **Code Editing Strategy**: Any frontend refinements for Phase 1 must be made in `defense_radar_system/public/` and then mirrored via the root build script.

## 6. A.4 Pre-Existing Baseline Issues & Forensic Analysis

The prompt specifically requested forensic investigation into 7 potential visual and operational discrepancies observed in baseline screenshots:

### 1. Scheduler Panels Looking Empty ("Live Decision Trace" & "Candidate Band Allocation State")
- **Investigation**: Inspected `defense_radar_system/public/js/app.js` (`renderPerBandStateTable()` L1276–L1285 and `renderDecisionTraceTable()` L1310–L1325), and `defense_radar_system/server.js` (L606–L615).
- **Finding**: In `server.js`, `simState.perBandState` and `simState.recentDecisionTrace` are initialized at server boot. However, on cold client load or if a browser connects during the first sub-second initialization interval before the first dwell cycle completes, `bandsData` and `traceData` arrays are temporarily empty (`length === 0`). In `app.js`, the render functions simply return early when `length === 0`, leaving the raw `<tbody>` elements blank with no "Awaiting dwell cycle..." placeholder or loading skeleton. Once the simulation runs its first dwell, the tables populate fully.
- **Remediation for Phase 1**: Add an informative empty state / skeleton row ("*Acquiring initial dwell cycle data...*") when `length === 0` rather than leaving an empty void.

### 2. Alert Timestamps Later Than Header UTC Clock
- **Investigation**: Inspected `defense_radar_system/incident_engine.js` (L142–L148) and `defense_radar_system/public/js/app.js` (L180–L195, L2140–L2155).
- **Finding**: The global header clock in `app.js` formats time explicitly using UTC (`new Date().toUTCString()` or UTC methods appending `" UTC"`). In contrast, the incident engine stamps incidents using local client machine time formatted with `new Date(timestamp).toTimeString().split(' ')[0]`. If the operator's machine is located in a positive UTC offset timezone (e.g., India Standard Time UTC+05:30), the alert timestamps show the local hour (e.g. `14:14:02`), while the header clock shows `08:44:02 UTC`.
- **Remediation for Phase 1**: Standardize all time displays to either UTC with explicit `' UTC'` badges or format both header clock and incident timestamps with consistent local/UTC indicators.

### 3. Webcam-Style Video with Fake Detection Boxes on Optical Page
- **Investigation**: Inspected `defense_radar_system/public/js/camera.js` (L45–L110).
- **Finding**: The video is **not** an actual webcam feed. There is a dormant code branch for `navigator.mediaDevices.getUserMedia` used during early prototype experiments, but the default and operational mode generates a synthetic night IR procedural horizon canvas. The bounding boxes (e.g. `CV-042 [94%]`) are procedurally projected from live radar track bearings intersecting the camera's FOV.
- **Remediation for Phase 1**: Clean up the UI framing so operators understand this is a synthetic thermal IR sensor simulation, removing any misleading "webcam" styling while preserving procedural bounding box rendering.

### 4. RF/ESM Axis Ticks (9.26, 9.46 ... vs 9.00–10.00 GHz Span)
- **Investigation**: Inspected `defense_radar_system/public/js/spectrum.js` (`CompactSpectrumAnalyzer.drawAxis()` L115–L165).
- **Finding**: The system simulates an agile digital receiver with a narrow instantaneous receiver window (IBW of ~50 MHz) tuned to a specific center frequency (e.g., 9.420 GHz). The plot renders FFT bins across the *instantaneous* receiver bandwidth, causing tick labels to reflect the active tuned sub-band (e.g., 9.26 to 9.58 GHz) rather than the entire 9.00–10.00 GHz macro surveillance envelope.
- **Remediation for Phase 1**: Add a dual-scale axis or a top miniature banner showing the full 9.00–10.00 GHz macro band with an illuminated cursor indicating the active instantaneous receiver sub-window.

### 5. TRK-021 Range Discrepancies (524m, 633m, 673m, 688m)
- **Investigation**: Traced `TRK-021` trajectory in `defense_radar_system/server.js` (L380–L420) and `defense_radar_system/test/test_final_presentation_acceptance.js`.
- **Finding**: `TRK-021` represents an inbound perimeter intruder with active velocity ($v = 21.8\text{ km/h}$) and an inward radial trajectory moving from outer range (688m) toward the 450m perimeter fence. As the simulation ticks forward, its range decreases continuously. The different numbers in the screenshots merely reflect different timestamps during simulation runs.
- **Remediation for Phase 1**: Normal behavior. Ensure the UI displays dynamic velocity vectors and range rate ($\Delta R/\Delta t$) clearly so operators immediately see that the target is in motion.

### 6. Optical Event Log vs Correlation Panel (TRK-021 Confirmed vs No Visual Confirmation)
- **Investigation**: Inspected `defense_radar_system/public/js/camera.js` (`updateCorrelation()` L220–L260 and `logOpticalEvent()` L280–L310).
- **Finding**: The Optical Event Log stores historical events chronologically. Earlier in the session, `TRK-021` crossed within `CAM-01` ($0^\circ$ North) line of sight, logging a positive acquisition. However, if the operator switches the active camera view to `CAM-03` ($180^\circ$ South), the live correlation panel evaluates instantaneous angular bearing against `CAM-03`'s FOV. Since `TRK-021` is at bearing $8^\circ$, it is outside `CAM-03`'s coverage sector ($150^\circ$ to $210^\circ$), correctly reporting "NO VISUAL CONFIRMATION".
- **Remediation for Phase 1**: Add an explicit subtitle in the correlation card: "*Target out of CAM-03 instantaneous field-of-view (Bearing 008° vs FOV 150°–210°). Last seen on CAM-01.*"

### 7. Scenario Lists on Tactical vs Simulation Pages Differ
- **Investigation**: Inspected `defense_radar_system/public/index.html` (L130–L140 and L1410–L1435) and `defense_radar_system/public/js/app.js` (L450–L490).
- **Finding**: On Page 1 (Tactical Context), `#scenarioSelect` offers 6 high-level operational scenarios:
